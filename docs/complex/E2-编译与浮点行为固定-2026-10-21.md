# E2 编译与浮点行为固定记录（2026-10-21）

## 结论

JaguarCore 与 SparrowCore 的 MSVC qmake 目标已显式使用 `/fp:strict`。SparrowWasm 的 CMake 目标按编译器选择浮点选项：MSVC 使用 `/fp:strict`，Clang/GCC 路径使用 `-fno-fast-math -ffp-contract=off`。目前没有发现 `/fp:fast`、`-ffast-math` 或源码级浮点控制 pragma。

选择 `/fp:strict` 是为了让 MSVC 2019 与更新工具集使用相同的非收缩浮点模型。Microsoft 文档说明 `/fp:precise` 在 Visual Studio 2022 之前可能默认允许 FMA 收缩，而 `/fp:strict` 不生成浮点收缩；`/fp:strict` 的额外浮点环境支持可能影响性能，本轮未做性能基准。[Microsoft Learn：`/fp` 浮点行为](https://learn.microsoft.com/en-us/cpp/build/reference/fp-specify-floating-point-behavior?view=msvc-170)。`/O2` 是速度优化组合，不等于 fast-math。[Microsoft Learn：`/O` 优化选项](https://learn.microsoft.com/en-us/cpp/build/reference/o-options-optimize-code?view=msvc-170)

## 实际编译选项

本轮在 Windows x64、Qt 6.5.3 `msvc2019_64`、MSVC 工具集 14.29.30133 下执行。`cl` 实际横幅版本为 14.29.30159.0。

Qt 6.5.3 的 qmake `win32-msvc` 基础配置提供 Debug 的 `/Zi /MDd`、Release 的 `/O2 /MD`，没有自行设置 `/fp:*`。项目现在在 JaguarCore 公共 `.pri` 与 SparrowCore 各 qmake 目标中显式设置浮点模型。Debug/Release 的优化和 CRT 选项不同，浮点模型相同。

JaguarCore 的 Debug/Release qmake 生成阶段会提示 `simd.prf` 找不到 `qt_build_config`；构建仍退出 0，AVX2 源的真实命令含 `/arch:AVX2`，标量分支也实际编译了 fallback 源。该 Qt feature 提示没有导致当前目标构建失败。

## 验证结果

- JaguarCore Debug、Release 和 `jaguarcore_no_avx2` Release 构建均退出 0；AVX2 与标量变体的实际编译选项已逐一检查。
- SparrowCore Debug、Release 构建均退出 0；两套 Tests 目标的 Debug、Release 编译也退出 0。
- SparrowCore 与 JaguarCore 的 Release 全量 runner 均退出 0。SparrowCore 两个 S07 旋转错误出口在 Debug/Release 下均退出 0，输出的阶段和错误分类一致。
- SparrowCore Debug全量runner此前退出3；本轮CDB全量复跑通过RNG、Sampling、LBF loss、SPP/BPP、Quantify并进入Separator组，后因长轨迹手动中止，结果不计为通过或失败。2026-10-22补丁前，针对已知`seed=4`顶层入口`--e5-seed4-top-level-optimize-compress`重新复现：CDB首次机会栈定位到`JaguarCore/Source/Collision/Quadtree/Quadtree.cpp:430`，`QuadTree::Constrict`抛出`std::logic_error("debug assertion failed: constricted_hazards has no partial child")`。调用链为`Constrict → RegisterIntoNode → RegisterHazard → CollisionEngine::RegisterHazard → Layout::PlaceItem → SPProblem::PlaceItem → Sparrow RunWorkerRound`（`SparrowCore/Source/Optimizer/Separator.cpp:274`）；worker收集后由`Separator::Run`第621行重新抛出，前一轮CDB在主线程确认第二机会未处理C++ EH异常。
- 对同一seed4顶层输入，Rust 1.98.1、锁定jagua-rs `f5e2b5f`的Debug测试`seed4_top_level_debug_retains_known_gls_nonfinite_assertion`退出0（4.30秒）；测试捕获的预期panic为`weighted loss should never increase: ∞ > NaN`（`CodeResource/sparrow/src/optimizer/worker.rs:122`）。补入C++ worker断言前，C++ Debug基线在worker放置阶段先触发Quadtree检查，而Rust Debug按已登记测试路径到达GLS断言；pinned Rust `qt_hazard.rs:113`有相同条件的`debug_assert!`，但本输入没有由该断言先退出。C++ MSVC 14.29 Release定向入口退出0，Rust pinned Release定向测试通过；`/fp:precise`Debug对照仍复现退出3，故该差异不是`/fp:strict`独有。
- 2026-10-22补丁前的第二次CDB几何快照复现同一首次机会异常：`hazard.presence=Partial`，`hazard.qtBbox=[0,-0.75,3,2.25]`；它与测试条带宽3、高1.5经`Container::Create`方形化后的CDE根边界一致。当前候选形状`shapeBounds=[0.5732928514480591,2.2504210472106934,2.5732927322387695,3.2504210472106934]`，整体位于根节点上边界之外，间隙约`0.000421047`；因此根节点的四个子象限都不可能与该形状边集相交，足以解释“无Partial子项”断言。输入条带fixture仅允许0度旋转、原始形状为`[0,2]×[0,1]`；由此可从CDB形状包围盒反推该候选平移约为`(0.57329285,2.25042105)`（这是由shape bbox重建的transform，不是调试器直接打印的`move.transform`）。worker现场仍是1个候选、1次移动、34次精确碰撞检查。CDB没有成功展开`std::unique_ptr<PartialHazard>`和`std::array<Rect2d,4>`，故未取得边数/端点及四象限逐项坐标。
- 为比较Rust首个Debug出口，本轮临时给现有Rust定向测试启用仓库logger；测试退出0并捕获预期GLS panic。Rust在panic前记录536条worker移动，最后一条为`(1.0017452,0.9984808) → (1.4980434,1.5003707)`，weighted loss为`∞ → NaN`；其新形状仍与CDE根相交。整条Rust Debug日志没有记录新放置形状完全越出根边界的候选。日志文件为临时路径`%TEMP%\JaguarRun-E2-Rust-seed4-debug-cargo.log`；Rust测试源的临时logger改动已撤回。
- pinned Rust在`worker.rs:122`的`debug_assert!(new_w_l <= old_w_l * 1.001)`位于放置候选和tracker更新之后；C++ `RunWorkerRound`当时在对应更新后直接结束循环并汇总`TotalWeightedLoss()`，没有该逐move Debug断言（这是2026-10-22补入映射前的状态）。该差异解释了Rust Debug为何在`∞ → NaN`处中止；基线材料没有捕获C++异常对应的全局worker轮次，不能确定两端的首次分歧轮次。没有证据表明Quadtree断言本身或`/fp:strict`是C++独有几何缺陷；Rust Debug日志也没有与C++异常候选相同的放置记录。2026-10-22的断言映射、红绿验证和当前结论见下方补充。
- Debug `--e5-fixed-nonfinite-worker-rounds`退出0；同一输入重复两次、各执行450轮三worker搜索，raw loss在断言容差内、weighted loss为NaN且两次结果位模式一致。该聚合夹具不复现上述Quadtree异常。
- JaguarCore Debug 全量 runner 退出 3。补齐 `JaguarCored.dll` 的运行时搜索路径后，CDB 捕获到未处理的 C++ 异常，调用栈为 `QuadTree::Constrict → RegisterIntoNode → RegisterHazard → runCollisionTests`；PDB 映射到 `TestCollision.cpp` 中 `coveringShape` 注册后的断言区域，抛出点为 `Quadtree.cpp` 的 `constricted_hazards has no partial child` 检查。该用例中的形状覆盖整个节点，所有子象限都可被归为 `Entire`，因此不会先产生 `Partial` 子项。锁定的 Rust 源 `qt_hazard.rs` 在相同阶段有同语义的 `debug_assert!`（第 113 行）；这是两侧源码共有的 Debug 路径，不是 `/fp:strict` 独有差异。Rust 侧此输入的 Debug 运行时结果本轮未单独执行。JaguarCore Release runner 退出 0；同工具集 `/fp:precise` Debug 对照也在该检查处退出 3。首轮未设置 DLL 搜索路径的直接启动返回 Windows `0xC0000135`，不计作 runner 结果。
- E2保持“部分”：MSVC Debug/Release选项与浮点模型已核实，Jaguar Debug退出对应Rust同构的Debug检查。2026-10-22在C++ `RunWorkerRound`补入与pinned Rust逐项语义一致的Debug-only损失正值、移动后加权损失单调及Tracker/Layout一致性检查；seed4顶层Debug回归先以既有Quadtree异常作为红测，更新后捕获Rust对应的weighted-loss断言；同入口Release重建后仍通过完整固定trace对拍。这把该seed4 Debug出口对齐到同类断言，但没有记录断言所处全局worker轮次，也不证明全部Debug worker轨迹等价。Emscripten SDK和实际编译命令当前不可用，不能声称Debug/Release结果完全对齐或WASM真实命令已核实。

## 2026-10-22 补充：Sparrow worker逐move Debug断言

- `SparrowCore/Source/Optimizer/Separator.cpp`在每次有效移动前检查该项的`ItemLoss(index) > 0`和`WeightedItemLoss(index) > 0`；`CollisionTracker::UpdateMovedItem`成功后检查`newWeightedLoss <= oldWeightedLoss * 1.001F`，再复核Tracker与Layout一致。所有新增检查都位于`#ifndef NDEBUG`，Release不执行这些分支。
- `SparrowCore/Tests/TestExploration.cpp`扩展seed4、单Compression worker的顶层Optimize定向用例。实现前先构建并运行回归，测试因捕获到`debug assertion failed: constricted_hazards has no partial child`而失败；加入worker断言后，同一测试退出0，并只在捕获异常文本含`weighted loss should never increase`时通过。
- 以MSVC 14.29重新构建SparrowCore Debug与SparrowCoreTests Debug，`--e5-seed4-top-level-optimize-compress`退出0。随后重新构建Release两目标，同一入口退出0；Release分支继续执行并通过已锁定的完整顶层trace比较。
- 该回归确认此输入下C++ Debug现在先暴露与Rust同类的逐move weighted-loss断言，之前的Quadtree异常不再是该测试的首个出口。测试没有记录局部/全局worker轮次或对拍完整Rust Debug轨迹；结论限于这一个seed、几何、配置及MSVC工具链。

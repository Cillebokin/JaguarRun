### 最终报告与返回（mod.rs:77-80）
- C++ 对应：SparrowOptimizer.cpp:197-239。
- 判定：正常内部结果路径基本等价；C++ 多两次终态恢复校验与若干异常出口，Rust 在此处不再恢复/校验。质量状态仍由 metrics 表达。
- 证据与说明：Rust `compression_phase` 返回内部 `best_sol` 后，`optimize` 直接执行 `report(ReportType::Final, &cmpr_sol)`（:77）并 `Ok(cmpr_sol)`（:80）；最终报告前没有 `SPProblem::restore`、`Layout::restore`、需求完整性检查或碰撞可行性检查。C++ 收到 `compressed.solution` 后的精确顺序是：先把压缩阶段 history 并入局部 history（SparrowOptimizer.cpp:193-195）→ `SPProblem::Create(instance)` → `validationProblem.Restore(solution)`（:197-212）→ 独立新建 `Layout(solution.layoutSnapshot.container)` 并再次 `Layout::Restore(snapshot)`（:213-222）→ 复制 metrics 并覆盖 seed/sampleCount（:225-227）→ `PublishSolutionReport(FINAL, phase=COMPLETE, iteration=0, collisionLoss=0, isFeasible=finalMetrics.feasible)`（:228-236；先追加 history，再同步调用 `OnSolution`）→ 返回 `SparrowOptimizationResult`（:238-239）。FINAL 回调前的任一终态恢复错误都会阻止 FINAL 报告与正常返回；FINAL 回调抛出的异常也会向调用方传播，阻止结果返回。局部 history 不随错误或异常返回，但此前已发生的 listener 回调无法撤销。
  - 这两次 Restore 会执行快照结构预检及 CDE 恢复；placement 与 dynamic-hazard 身份/数量一致性依靠 Debug 断言，Release 不会因这一 mismatch 退出。不调用 `ValidateSPSolution` 或 `Layout::IsFeasible`，因此不会仅因需求未满足或布局相互碰撞而拒绝。终态 `isFeasible` 取 `compressed.metrics.feasible`，不是这两次 Restore 的结果。`TestEmptyLargeAndPartialWarmStartMatchRust` 已核对 partial 与重叠 warm-start 在终态仍能返回、发出 FINAL 报告且 `isFeasible=false`；对应 Rust reference 为 `optimizer_partial_warm_start_reference.rs`。这证明质量失败通过 metrics 报告，不证明任意快照均可恢复。
  - C++ 错误出口要分开记录：`SPProblem::Restore` 返回的 `Result` 错误被映射为 `ErrorCode::Infeasible`（message: `Sparrow optimizer produced an invalid final solution`）；独立 `Layout::Restore` 的 `Result` 错误也映射为 `Infeasible`，但 message `Sparrow optimizer produced a geometrically infeasible solution` 过度声称几何不可行，实际没有做碰撞可行性判断。Debug 一致性断言和 Debug 需求下溢检查可能抛异常；越界 item index 会抛 `std::out_of_range`；这里均没有 catch，因此不会走上述 `Result<...>::FromError` 映射。Rust 在此处既没有这些恢复 Result 出口，也没有对应的终态报告前恢复异常点。
  - 终态快照来自构造、探索和压缩的内部状态；用户提供的 warm-start 在优化开始处已先经 `MakeWarmStart`/`SPProblem::Restore` 处理。现有 reference 已覆盖可恢复的 partial/overlap 终态，但没有证据表明合法输入能确定性触发最终 Result 错误；独立破坏“压缩产物”的快照需内部注入点，当前不为此添加生产钩子。因此，终态损坏快照行为仍属于**内部不变量失效时的防御出口，未做跨语言故障注入对照**，不应与公开 Restore 输入边界混为一谈。
  - 报告时序：两侧压缩完成后均发布一次 FINAL 解报告，再正常返回；C++ 把报告加入 history 后才同步调用 `OnSolution`，并在报告元数据中补充 `phase=COMPLETE`、`iteration=0`、`collisionLoss=0` 和 `isFeasible`。FINAL 回调 stop 请求不会触发后续优化工作；异常会阻止正常返回。返回形态仍不同：Rust `Ok(cmpr_sol)`（SPSolution）→ C++ `SparrowOptimizationResult{solution, metrics, history}`（:238-239，metrics.sampleCount 取构造阶段计数 :227，reject/exact 取两阶段聚合，S06/S07）。
- C++ 额外：无终止器重载入口 `Optimize(instance, config, listener)`（:242-251，自建 terminator+Start）——Rust 侧对应 bench/cli 的用法；既定差异：Rust `Terminator` 是 trait（util/terminator.rs:5-14），C++ 是具体类（OptimizationTerminator.h:22-40，S20）。

### `minimum_strip_width`（mod.rs:85-122）
- C++ 对应：Explore `Exploration.cpp:61-144` 与 Compression `Compression.cpp:56-127` 各有一份实现；Compression 的 f32/f64 运算次序与 Explore 的全离散角 `INFINITY` 下界均已按 Rust 定向对齐，并有对应 reference。两份 C++ helper 仍是独立实现。
- 判定：已确认的 Compression 最小宽度阈值、Explore 正无穷下界及合法输入下离散旋转高度容差临界边界均通过定向验证；其他上游几何精度和一般旋转输入仍需覆盖。
- 证据与说明：
  1. 面积下界：Rust 每项先读取 `shape.area` 的 f32 值，再经 `f64::from` 累加（:89-94）。Explore 和 Compression C++ 现在均先将 `CollisionShape().Area()` 转成 float，再以 double 累加这些 f32 输入、将商转回 float 并执行 f32 容差乘法（Exploration.cpp:79-87；Compression.cpp:67-78）。旧 Compression double 路径已移除；一般导入几何的上游 area 是否逐位相同仍未由该公式测试证明。
  2. 离散旋转宽度下界：Rust 对 None/Discrete 旋转逐项计算，跳过 Continuous，并按旋转 bbox 和直径容差筛选（:97-118）。Compression C++ 将角度、直径容差、bbox 宽高都转入 f32 后比较/减法（Compression.cpp:86-127），变换仍使用 JaguarCore `TransformedRustF32`；源码路径对应，不代表所有角度和几何逐位相同。若所有离散角都无法满足容器高度，Rust 的 fold 初值会保留为 `INFINITY`；Compression 与 Explore 现均无条件并入 `itemWidth`，得到同一正无穷下界。Explore 该边界由 `ExplorationMinimumWidthInfinityRustReference.tsv` 和 C++ 实际 Explore 回归验证，但 fixture 不比较非法初始角下的报告分类。另有 8×2 矩形 `{0°,90°}` 用例，以合法 0° 初始布局和跨越高度容差的相邻 f32 容器高核对最小宽度位模式；它覆盖筛选阈值，不外推至一般变换精度。
  3. inset：Rust 先计算 f32 `width_inset = strip_width - container.width()`，再以 f32 将其加到最小宽度（:88,121）；Compression C++ 也以 float 计算 inset 和返回值（Compression.cpp:63-64,127），不再使用旧的 double 计算及非有限/非正结果归零。
  4. **真实阈值边界**：`CompressionMinimumWidthRustReference.tsv` 由锁定 Rust helper 记录最小宽度位模式 `0x3fffffe8`，并分别调用实际 `compression_phase`。`below` 探针的 step bits 为 `0x3f00000d`、next-width bits 为 `0x3fffffe6`，低于阈值且 progress count=0；`at_or_above` 的 step bits 为 `0x3f00000c`、next-width bits 为 `0x3fffffe8`，恰等阈值且 progress count=1。C++ `TestCompressionMinimumWidthMatchesRustBoundary` 精确比较 min-width/next-width 的 f32 bits，并运行实际 `Compress` 比较压缩 progress 次数；Debug/Release 均通过。该证据只锁定单件 2×2 方形、宽/高 4 的边界，不代表任意 shape、旋转集合或完整压缩搜索都相同。
  5. Rust 注释 "ponytail: continuous rotations use only the area bound"（:101）→ C++ 两条路径均跳过 Continuous：一致。
  6. 差异（实现形态）：Rust 复用 `shape_buffer` 单缓冲反复 transform_from（:105-113）；C++ 每角新建变换结果：性能形态。**双侧副本**：Explore 与 Compression 各保留一份 helper，维护上可能漂移；现有边界测试分别覆盖 Compression 阈值和 Explore 正无穷下界，不证明两份 helper 在其他输入上完全一致。

## 第二节. `SppLbfOptimizer`（SppLbfOptimizer.cpp:34-173）vs lbf.rs 构造流程

  3. **与 SparrowLbfBuilder 的差别**：a) **无 `2×Σ直径` 宽度上限**（只查 32 次尝试上限）——Rust lbf.rs:104-111 有该上限；b) **宽度增长比默认 1.1 vs SparrowLbfBuilder 的 1.2**（LbfConfig.h:24 vs SparrowConstructorConfig widthGrowthRatio=1.2，LbfConfig.h:75）——两个 C++ 入口的默认不同，Rust 只有 1.2；c) `localSearchFraction` 参与 sampleCount 统计（:121-124，失败一轮计 `samplesPerItem - floor(samplesPerItem*localSearchFraction)`）——Rust 无此统计口径（n_evals 直接累计）。判定：差异（统计口径；`localSearchFraction` 默认 0.2 时失败轮计 0.8×5000=4000，而实际评估数未必——观测数据偏差，非行为差）。

## 结论
三阶段控制流与子 seed 取得顺序从源码可对应，且有 seed=3 warm-start、seed=42 默认 LBF 预算下的受控 cold-start、默认探索/压缩配置 cold-start、seed=43/42 的 Explore→Compress 状态交接、两阶段零时限立即退出、250 ms FailureBased deadline crossing、2 s TimeBased deadline crossing，以及构造失败和探索初始报告后立即停止的 Rust reference。TimeBased 到期用例在首个 progress callback 等待 2100 ms 且不发 stop 请求；计时器到期后已开始的一个 attempt 仍完成，separator 为 success/0 eval/move/iteration，最终可行宽度约 3.68，并逐项比较 phase/report/step/separation/placement trace。另一个正时限 TimeBased 曲线用例采集五个步长与各自回调时间，核对 Rust/C++ 起点及线性斜率；它由 listener 在第五个步长处停止，不等价于 deadline 到期。默认配置 cold-start 核对阶段参数、报告/阶段顺序、分离计数和最终摆放，listener 在探索与压缩各自首个 separation result 后请求 phase stop；它不运行完整 9 分钟/60 秒自然阶段时限。零时限 fixture 证明两阶段均跳过 separator 并保留同一构造布局；250 ms 正时限 fixture 证明探索在延迟回调后不进入 separator，压缩则在等待越过期限后仍完成当前尝试收尾，最终布局由宽度 4.0 压缩到 3.96。minimum-width boundary fixtures 分别验证 Compression 单件方形输入下的 Rust f32/f64 运算顺序和 `< min_width` 门槛、Explore 在所有离散角均不适配容器高度时保留 Rust 的 `INFINITY` 下界，以及合法 0° 初始解下离散旋转高度容差两侧的最小宽度位模式；后两项不覆盖一般旋转/上游几何差异。上述 TimeBased 测试的等待是可重复触发期限的方法，不代表未经等待的完整限时搜索。deadline 相等瞬间轮询、完整默认时限运行仍未覆盖。其他退出 fixture 证明在列明实例与触发点下，构造失败先于 phase callback，phase stop 可在下一阶段重置，压缩会在成功一次后到达最小宽度边界；不能据此外推其他错误输入或全部退化域。PhaseReference.tsv 仍只是 C++ 自回归数据。handoff fixture 已证明 Rust 在 exploration 失败报告后的 disrupt 会让 separatorState 与 best solution 不同，并验证 C++ 分别传入压缩。Explore 的已确认全离散角 `INFINITY` 下界差异现已按上述 reference 修复，合法初始输入的相邻 f32 高度阈值也已对齐；两侧上游几何数值的一般性仍未覆盖。SparrowLbfBuilder 的另一 Rust fixture 使用 64/0/1 配置且以容差比较宽度/密度。SppLbfOptimizer 是独立入口（排序二态、增长比 1.1、无宽度上限）；BppLbfOptimizer 是 Rust sparrow 不存在的 BPP 额外变体。
